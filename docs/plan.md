# mix-assist — рассуждения, идеи, план

Дата: 2026-10-16. Статус: план, кода нет.

## 0. Рамка

- **Что строим:** пилот агента для себя. Он слушает мультитрек, понимает, что звучит и что можно улучшить, крутит параметры и сам проверяет результат.
- **Не цель:** продукт или статья. Цель — рабочая штука плюс понимание, что модели реально умеют.
- **Приоритеты** (из твоих ответов): рабочий ассистент, аудиограмма моделей, обучение моделей.
- **Роли (твоя схема):**
  - Music Flamingo (MF) — архитектор. System 2: медленно, словами, решает «что и зачем».
  - Jev-модель — рулевой. System 1: быстро, без слов, решает «какой вариант лучше». Получает задачу от MF и доводит звук до цели.
- **Материал:** свои мультитреки.
- **Железо:** Mac (разработка), NVIDIA 8 ГБ под Windows, Modal (тариф Starter: $30/мес бесплатных кредитов).
- **Интерфейс MVP:** CLI + файлы.

## 2. Ключевые соображения (что меняет план)

### 2.1. Модели слышат только до 8 кГц и, скорее всего, в моно

- Sori ресемплит в 16 кГц, clef-omni принимает 16 кГц моно — это написано в карточках.
- MF, AudioJev и d1 построены на энкодерах типа Whisper/FastConformer. Там тоже 16 кГц; подтвердим тестом.

Что из этого следует:

- **Выше 8 кГц модели ничего не слышат**: «воздух», искристость тарелок, верх сибилянтов. Эту зону оценивают DSP-метры, а не модели.
- **Стерео (панорама, ширина), скорее всего, не слышат вовсе.** Поэтому панораму откладываем. Моно-даунмикс моделям делаем сами — тогда их поведение предсказуемо. Тест T4 проверит, используют ли они стерео, если его дать. Заодно он поймает загрузчик, который берёт только левый канал: тогда гитары, панорамированные вправо, для модели исчезают.
- **Низ модели видят грубо.** У Whisper-подобных энкодеров окно 25 мс, это бин ~40 Гц. Ниже ~120 Гц (кик против баса) — кандидат в слабые места аудиограммы.

### 2.2. Jev не выдаёт параметры — он выбирает

У Jev-моделей нет генерации текста, только вероятности по заданным вариантам. Поэтому «Jev рулит» значит **поиск по отрендеренным кандидатам, где Jev — датчик**. Так работает инженер с фейдером: двигает и слушает, пока вокал не «сядет».

Есть два режима датчика:

- **абсолютный:** `score` по шкале «слишком тихо … баланс … слишком громко» для каждого кандидата. Через `ask_batch` это один forward на всех;
- **сравнительный:** `choice` «в какой из 8 версий вокал сидит лучше всего». У Sori 8 клипов помещаются в один state.

Какой режим надёжнее, решает этап 0.

### 2.3. MF передаёт задачу Jev формальной спекой, а не свободным текстом

MF пишет «перцептивные юнит-тесты», Jev их прогоняет, поиск подбирает параметры, пока тесты не пройдут:

```json
{
  "issue": "level.vocal",
  "why": "в припеве вокал тонет под гитарами",
  "clip": "chorus_1",
  "question": {"type": "score",
               "instructions": "How loud is the lead vocal relative to the rest of the mix?",
               "criteria": ["far too quiet", "a bit quiet", "balanced", "a bit loud", "far too loud"]},
  "target": 2.0,
  "knobs": {"vocal.gain_db": [-3, 9]},
  "guards": ["overall.natural", "harsh.vocal"]
}
```

Словарь проблем **закрытый**: в него входят только формулировки вопросов, прошедшие аудиограмму (этап 0). MF выбирает проблемы из словаря и заполняет слоты. Её вывод считаем недоверенным и проверяем по словарю и списку дорожек.

### 2.4. Двусторонние шкалы против «взлома» судьи

Вопрос «вокал разборчив?» поиск «решит», подняв вокал на +12 дБ. У шкалы «тихо / баланс / громко» с целью «баланс» оптимум внутри диапазона. Так же строим вопросы о тембре: «тонко / баланс / мутно», «глухо / ясно / резко».

Бонус: цель на шкале — число. Его можно сдвинуть под свой вкус без всякого обучения: «вокал чуть горячее» = 2.3.

### 2.5. Песочница «испорти → почини» даёт известный правильный ответ

Берём твой готовый микс (стемами) как эталон, портим его известными сдвигами gain/EQ, агент чинит. Правильный ответ известен точно, поэтому получаем:

- честную метрику: остаточную ошибку в дБ и расстояние до эталона;
- оракулы по компонентам: видно отдельно, ошибся ли MF в диагнозе или Jev в рулении;
- сколько угодно данных с точными метками для этапа 3.

Одна и та же машинка кормит этапы 0, 1–2 и 3.

Тонкость: после нормализации громкости «вокал −3 дБ» ≡ «всё остальное +3 дБ». Поэтому ошибку меряем в относительных уровнях.

### 2.6. Гудхарт: оптимизируем по одному судье, проверяем другим

Если оптимизируем по Sori, проверяем не Sori, а hold-out судьёй (clef-omni или MF в режиме Jev) и твоими ушами вслепую. Ещё три защиты:

- кандидат «ничего не менять» всегда в наборе;
- шаг поиска не меньше порога различения (JND);
- guard-вопросы проверяют, что ничего не стало хуже.

### 2.7. Перекосы судей

- громкость → все кандидаты выравниваем по LUFS;
- позиция варианта → 2–3 перестановки порядка, ответы усредняем. У AudioJev это часть обучения, у Sori — неизвестно;
- dtype → замеры Sori делаем в fp32, как советует карточка.

### 2.8. MF знает MUSDB

MUSDB-HQ есть в обучающих данных MF, поэтому оценки на нём будут завышены. Твои мультитреки модели не видели — это плюс твоего выбора.

### 2.9. Каждая модель — отдельный сервис

Sori требует `transformers>=5.13`, clef-omni тестировали на 5.10.2, у MF свой класс — в одном окружении они не уживутся. Поэтому каждая модель живёт в своём venv или Modal-образе за HTTP, а оркестратор ходит ко всем одним клиентом:

- Sori, clef-omni и d1 совместимы с Jev/SystemOne API;
- для AudioJev нужен тонкий адаптер.

Сменить модель = сменить `base_url`.

## 4. Выбор: сначала уши, потом руки, потом голова, потом учёба

Три стратегии: agent-first, model-first, measure-first. Беру **measure-first**:

- каждый этап даёт штуку, которой можно пользоваться, и число;
- ошибки видно по отдельности: диагноз MF, руление Jev или бедное пространство действий;
- данные для обучения выпадают из той же песочницы;
- покрывает все три приоритета: аудиограмма (этап 0), ассистент (1–2), обучение (3).

Архитектура:

```
                      цель (опц.): «вокал вперёд»
                                │
стемы ─┬─► [MF — архитектор, System 2] ──► спека: проблема, вопрос, цель, ручки, guard'ы
       │          ▲                                   │
       │          │ финальный разбор «до/после»       ▼
       │          │                    [Рулевой — Jev + поиск, System 1]
       │          │                    рендер кандидатов: gain/EQ → сумма → LUFS → моно
       │          │                    Jev: score/choice → зум → стоп по цели или JND
       │          └──────────── микс + params.json + лог ◄──┘
       └─► [DSP-метры] LUFS по стемам, энергия полос, маскинг, всё, что выше 8 кГц
Проверка: hold-out судья (другая модель) + твои уши вслепую
```

## 5. Пространство действий (решение)

На этапах 1–2 у каждого стема 5 ручек, все в зоне, которую модели слышат:

| Ручка | Диапазон | Парная шкала (цель — середина) |
|---|---|---|
| `gain_db` | −12…+12 дБ | тихо ↔ баланс ↔ громко (относительно микса) |
| `hpf_hz` | 20…250 Гц | мало низа ↔ баланс ↔ гудит |
| `lowmid` (колокол) | 150–600 Гц, −9…+6 дБ, Q≈1.5 | тонко ↔ баланс ↔ мутно/коробочно |
| `presence` (колокол) | 1.5–5 кГц, ±6 дБ, Q≈1.5 | глухо ↔ ясно ↔ резко |
| `shelf` (полка) | ~5 кГц, ±6 дБ | тускло ↔ баланс ↔ ярко (выше 8 кГц — только по DSP-метру) |

Плюс глобальные guard-вопросы:

- «естественно ли звучит микс» (`score`);
- «разборчив ли вокал» (`noul`) — только как guard, не как цель.

Диапазоны и шаги поиска уточняем по аудиограмме.

Правило расширения: новая ручка (компрессор, реверб, панорама) появляется, только если аудиограмма показывает ≥75% различения при реалистичной величине изменения.

## 6. План по этапам

Размеры: S — небольшой, M — средний, L — большой.

### Этап 0 — песочница и аудиограмма (M)

**Цель:** выяснить, что модели слышат, и выбрать рулевого.

**Строим:**
- рендер: стемы → gain + EQ → сумма → LUFS → моно;
- «портилку» (известные сдвиги gain/EQ);
- выбор фрагментов: 10–15 с, самые плотные места;
- кэш ответов моделей по хэшу (аудио + вопрос). Сам рендер дешёвый, кэшировать его не нужно.

**Материал:** 3–5 твоих готовых миксов стемами (вокал, барабаны, бас, гитары, остальное), без мастер-цепочки, float WAV; по 2–3 фрагмента на песню.

**Эксперименты:**
- **T1, абсолютный режим:** score-шкалы на сдвигах уровня (−9…+9 дБ) и EQ (колокол ±3/6/9 дБ на частотах 125…4k, плюс 8k и 12k для проверки слепоты) → психометрические кривые. Вариант с соло-подсказкой (R).
- **T2, 2AFC:** эталон против испорченного, порядок случайный → точность в зависимости от величины сдвига. Моделям, которые берут одно аудио, отдаём склейку «A, бип, B».
- **T3, 8 вариантов:** найти эталон среди 7 испорченных.
- **T4, перекосы:**
  - громкость: ±1 дБ без выравнивания;
  - позиция: перестановки порядка;
  - стерео: обмен L/R и изменение ширины (S×0 / S×1.5) — для модели с моно-даунмиксом вход идентичен;
  - слепота выше 8 кГц.
- **T5, MF словами:** спрашиваем «что не так с миксом» на испорченных клипах и смотрим, назвала ли она нужный стем и проблему. Отдельно проверяем «до/после» склейкой с бипом.
- **T6:** MF в режиме Jev на заданиях T1–T3.

**Модели:** Sori и d1-omni — локально; AudioJev, clef-omni и MF — на Modal.

**Результат:**
- аудиограмма каждой модели: порог различения по стему × полосе, в виде тепловой карты;
- таблица перекосов и калибровка;
- выбранный рулевой и словарь вопросов;
- команда `meter`.

**Идём дальше, если:** хотя бы один Jev различает вокал ±3 дБ и ≥2 EQ-зоны при ±6 дБ с точностью ≥80% (после устранения позиционного перекоса).
Иначе — сначала дообучить Jev на песочнице (этап 3a) и вернуться.

**Деньги:** ≈ $10–20 на Modal — укладывается в бесплатный лимит.

### Этап 1 — рулевой на оракульных спеках (S–M)

**Цель:** показать, что Jev + поиск чинят заранее известную проблему.

**Строим:** зум-поиск:

```
x = текущее значение; шаг = диапазон / 8
повторять:
    кандидаты = 7 точек вокруг x с этим шагом + сам x
    рендер (LUFS, моно) → Jev (2–3 перестановки, среднее)
    если лучший == x или шаг < JND → стоп
    x = лучший; шаг /= 2
проверка: цель на шкале достигнута, guard'ы не хуже, hold-out судья согласен
```

**Эксперименты:** сначала одна проблема, потом 2–3 одновременно.
Бейзлайны: ничего не делать, статистика твоих миксов, случайный поиск, DSP-эвристика.

**Результат:** команда `fix <песня> --issue level.vocal` и остаточная ошибка в дБ.

**Идём дальше, если:**
- медианная остаточная ошибка ≤ JND;
- починено ≥70% задач;
- результат лучше, чем «ничего не делать» и случайный поиск;
- hold-out судья согласен в ≥70% случаев.

### Этап 2 — архитектор и полный цикл = MVP ассистента (M)

**Цель:** рабочий ассистент на твоих черновых миксах.

**Строим:**
- **MF-цепочка:**
  1. подписи стемов (по одному вызову на стем);
  2. разбор микса с рассуждением;
  3. выбор проблем из словаря в JSON (с валидацией и повторами);
  4. спека → рулевой;
  5. финальный разбор «до/после».
- **`run <папка стемов> [--goal "..."]`** → `mix.wav`, `params.json`, `report.md`. Отчёт человеческим языком, например «Vocals +2.5 дБ; Guitars −4 дБ @ 320 Гц, Q 1.5» — это легко перенести в DAW руками.
- **`ab a.wav b.wav`** → слепое прослушивание в терминале, ответ пишется в jsonl.

**Эксперименты:**
- в песочнице — оракулы по компонентам (диагноз отдельно, руление отдельно);
- абляции: с метрами и без; MF против «глухой» текстовой LLM с метрами.

**Идём дальше, если:**
- в песочнице ошибка падает на ≥50% относительно испорченного микса;
- правильный диагноз попадает в top-3 MF в ≥60% случаев;
- на твоих черновиках вслепую версия агента лучше в ≥60% из ≥20 пар.

### Этап 3 — датасет действий и дообучение (L)

**Цель:** дообучить обе модели там, где аудиограмма и этап 2 показали дыры.

**Датасет MixActions** («рассуждение → действие») из четырёх источников:
1. **Песочница:** (аудио [+ метры]) → (проблема, ручка, направление, величина). Метки точные, это основной объём.
2. **MixAssist:** LLM вытаскивает действия из реплик эксперта → рендерим → оставляем только те, где Jev/метры подтверждают направление эффекта.
3. **MixParams:** распределения реальных ходов инженеров → из них делаем реалистичные порчи.
4. **Твои сессии:** принятые и отвергнутые действия, результаты A/B.

**Сплит по песням:** тестовые песни никогда не попадают в обучение.

**Порядок:**
- **3a. Jev.** Учим на песочнице: выбор эталона среди кандидатов и шкалы, размеченные по известным сдвигам. Порядок вариантов перемешиваем (идея RD-SKL из AudioJev). Обучаем локально на 8 ГБ (LoRA или только reader) или на Modal L40S. Затем перемеряем аудиограмму — пороги должны упасть.
- **3b. MF.** LoRA на (аудио [+ метры]) → (разбор в стиле MixAssist + JSON-спека). Modal A100-80/H100, ≈ $10–30. Затем перемеряем метрики этапа 2.
- **3c (опционально).** RL архитектора с наградой из песочницы.

**Успех, если:** на отложенных песнях пороги ниже и/или ошибка end-to-end ниже, чем до обучения, и вслепую ты предпочитаешь новую версию.

Если своих песен меньше ~20–30, разнообразия для обучения мало. Тогда можно добавить публичные мультитреки — только в train (опционально).

## 8. Риски

| Риск | Вероятность | Что делаем |
|---|---|---|
| Модели не слышат разницу уровня/EQ в миксе | высокая | Этап 0 это сразу покажет. План Б — дообучить Jev на песочнице (3a) до сборки петли |
| Слепота выше 8 кГц и к стерео | почти наверняка | Ручки только в слышимой зоне; верх и стерео оцениваем метрами |
| Гудхарт: поиск находит слабые места судьи | средняя | Двусторонние шкалы, «ничего не менять» среди кандидатов, hold-out судья, уши |
| Перекосы по громкости и позиции | средняя | LUFS, перестановки порядка |
| MF не держит формат JSON | средняя | Закрытый словарь, валидация, повторы |
| MF плохо работает с несколькими аудио в одном запросе | средняя | Одно аудио на вызов; «до/после» — склейкой с бипом |
| Конфликты версий transformers | высокая | Каждая модель — сервис со своим окружением |
| Нет обучающего кода Sori | средняя | Свой цикл: логиты по вариантам + кросс-энтропия. Запасной вариант — d1-omni (открытый бэкбон LFM2.5-Encoder) |
| Мало своих песен для обучения | средняя | Сплит по песням; опционально публичные мультитреки в train |
| Лицензии MF/Sori (некоммерческая / академическая) | для личного ресёрча низкая | Не распространять производные веса |

## 11. Ревизия после этапов 0–1 (2026-10-16, по измерениям)

Измерено, не предполагается:

- d1-omni-600M — глухая (experiments/001).
- AudioJev — слышит уровень вокала монотонно (ρ=0.8), специфично, JND
  ~3–4.5 дБ; бисекция в fix.py сходится на «идеале модели», но идеал ≠
  референс (смещение 1–8 дБ, зависит от формулировки) (002–006).
- Music Flamingo — слепа к уровням (−6 дБ вокала = «balanced» даже при
  прямом вопросе, clean≡spoiled, стерео/моно без разницы); семантика
  (инструменты/жанр/настроение) работает (007).
- 2AFC-склейка «половина|бип|половина» не работает у Jev-моделей —
  лейбл-перекос, аудио не влияет (доказано одинаковыми conf).
- EQ (bell 300 Гц ±9 дБ) AudioJev почти не слышит.

### Новая развязка ролей (заменяет «MF ставит диагноз»)

```
MF (художник)      → свободные наблюдения/гипотезы + рекомендации
                     («добавить струнных» тоже разрешено — идёт в блок
                     замечаний, не в исполняемую спеку)
DSP-метры (физика) → LUFS по стемам, энергии полос, маскировочная
                     матрица, crest  [meters.py — не написан]
Архитектор (LLM)   → фьюзит заметки MF + отчёт метров (+интент юзера)
                     → валидирует гипотезы MF метрами → спека задачи
Jev (исполнитель)  → бисекция/кандидаты до калиброванной цели
```

MF = генератор гипотез, метры = валидатор, архитектор = синтез,
Jev = исполнение. Честный бейзлайн: связка метры+Jev без MF — MF
входит в цикл только если её художественный слой доказуемо добавляет.

### Обучение «рассуждению» (по MixAssist + MixParams + песочница)

Чему реально учить (не перцепцию — её дёшево не доучить, а стиль
рассуждения + заземление в действия):

1. **MixAssist** (640 ходов, текст на HF, аудио на Zenodo) — стиль
   инженерного анализа и диалога.
2. **MixParams** (2345 строк: track_type/subtype + parameters JSON
   {gain, pan, EQ, comp, reverb} + LUFS стема) — заземление в параметры;
   track_type мапится на наши стемы.
3. **Песочница** — синтетика «(порча + метр-отчёт + описание MF) →
   правильный диагноз + спека задачи». Этого звена нет ни в одном
   датасете — генерируем сами (шаблон/учитель-LLM поверх известной
   порчи).

Порядок важен: сначала зафиксировать формат входа (метр-отчёт +
описание → спека), потом под него генерировать данные и делать LoRA
для MF на Modal (~$10–30). До формата — дообучение преждевременно.
